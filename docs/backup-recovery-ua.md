# Резервне копіювання та відновлення INCORA People

## Що зберігає експорт з адмін-панелі

Розділ **Налаштування → Огляд → Резервна копія** формує JSON-файл із усіма
рядками D1, зокрема Assets, Documents, Announcements, Time projects, Knowledge
base та історією профілів. Для кожного приватного файлу в ньому також є точний
`objectKey` з R2.

Експорт містить персональні дані. Зберігайте його лише в обмеженому сховищі,
з доступом для супер-адміністраторів, і не додавайте до Git.

## Обов'язкова пара для повного відновлення

D1 та R2 — різні сервіси. JSON-експорт відновлює метадані й маніфест ключів,
але не копіює бінарний вміст R2. Для повної резервної копії завжди потрібні:

1. SQL-експорт D1 або JSON-експорт з адмін-панелі;
2. копія **всього** production R2 bucket у окремому bucket / сховище;
3. однакова дата й час для обох копій.

У метаданих `stored_files` також зберігається статус перевірки
`unscanned/clean/quarantined/failed`. Під час відновлення не підміняйте цей
статус вручну: якщо `FILES_REQUIRE_SCAN=true`, доступ дозволений лише після
нового рішення scanner-а через підписаний callback.

## Локальний restore-drill

Перед production-релізом можна перевірити відтворюваність JSON-снапшота без
ризику для D1. Скрипт нижче застосовує поточну історію міграцій до ізольованої
in-memory SQLite-бази, імпортує всі таблиці з експорту, повторно вмикає тригери
та перевіряє зовнішні ключі, `integrity_check`, кількість рядків і унікальність
маніфесту R2. Він не записує в Cloudflare D1 і не копіює файли в R2.

```bash
BACKUP_FILE=/secure/path/incora-people-backup-YYYY-MM-DD.json \
  npm run test:backup-restore
```

Очікуваний результат починається з `BACKUP_RESTORE_DRILL` і має містити
`foreignKeys: 0` та `integrity: "ok"`. Це перевірка D1-метаданих, а не заміна
окремого копіювання бінарних R2-об'єктів і повного контрольного відновлення в
тимчасові Cloudflare-ресурси.

У Cloudflare налаштуйте окремий bucket для резервних копій та запускайте
копіювання об'єктів за розкладом зовнішньою CI-задачею або дозволеним S3/R2
інструментом. Не замінюйте робочий bucket вручну без тесту відновлення.

## Перед міграцією або ризиковим релізом

```bash
mkdir -p backups
npx wrangler d1 export incora-people --remote \
  --output="backups/incora-people-$(date +%F-%H%M).sql"
```

Після цього завантажте JSON-експорт із адмін-панелі й зафіксуйте ідентифікатор
R2 snapshot у журналі релізу. Так можна зв'язати дані та файли одного стану.

## Контрольне відновлення

Раз на квартал відновіть копію в окремі тестові D1 і R2 ресурси, а не у
production. Перевірте:

1. кількість працівників, записів часу, активів, документів та Knowledge-статей;
2. наявність кожного `objectKey` із JSON-маніфесту у тестовому R2;
3. відкриття кількох документів, чеків і вкладень Knowledge base;
4. вхід тестовим працівником та супер-адміністратором.

Повернення Worker до попереднього deployment не відкочує D1 або R2. Дані
відновлюються лише за погодженим планом і з перевіреної копії.
