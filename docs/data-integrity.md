# Цілісність даних INCORA People

## Джерела правди

- `employees` зберігає профіль працівника, але організаційні поля завжди прив’язані зовнішніми ключами до `org_units`, `reference_values` і `employment_types`.
- `users.employee_id` задає однозначний зв’язок облікового запису з працівником.
- `system_settings` містить змінні параметри системи: захищені суперадмінські адреси та параметри створення нового працівника.
- `leave_ledger` є незмінним журналом використання відпусток; `leave_balances.used` — похідний кеш, який перераховують тригери БД.
- `stored_files` містить метадані приватних R2-об’єктів; права доступу та, за
  потреби, статус malware-сканування перевіряються сервером перед видачею файлу.

Текстові назви посад, підрозділів, рівнів, технологій і типів зайнятості залишені в профілі лише як читабельний знімок. Тригери не дозволяють їм розійтися з канонічним довідником і каскадно оновлюють їх після перейменування.

## Гарантії на рівні БД

- заборонені неактивні, відсутні або невідповідні довідникові значення;
- заборонені цикли керівників та оргструктури;
- один працівник не може мати кілька користувацьких акаунтів;
- один працівник не може мати кілька одночасно відкритих таймерів;
- запити на відпустку не можуть накладатися, перевищувати залишок або мати дробовість, відмінну від половини дня;
- погоджений запит не можна непомітно переписати, а переходи статусів обмежені дозволеним workflow;
- захищеного суперадміна не можна видалити чи понизити в ролі;
- зовнішні ключі контролюють зв’язки усіх модулів.

Ці правила діють для вебу, мобільного API, імпорту та будь-яких майбутніх write-path, а не лише для поточних форм UI.

## Атомарні операції

Створення й повне редагування працівника, зміна системних параметрів та керування типами зайнятості виконуються через D1 `batch`. Зміна статусу відпустки, запис у ledger і перерахунок балансу виконуються в одній SQL-транзакції тригерами. Побічні сповіщення можуть повторюватися незалежно, не пошкоджуючи основний стан.

## Контроль і резервне копіювання

`GET /api/admin/integrity` доступний адміністраторам і перевіряє зовнішні ключі, облікові записи, оргструктуру, менеджерів, технології, ledger, річні баланси, файли й таймери. Та сама інформація показується в адмінських налаштуваннях.

Адмінський JSON backup включає керовані довідники, системні параметри й журнал відпусток. R2-файли резервуються окремо за переліком `objectKeys` із backup.

## Безпечний порядок релізу

1. Зробити D1 backup і копію R2.
2. Виконати `npm run quality` та `npm run build`.
3. Застосувати міграції D1 перед публікацією коду.
4. Переконатися, що `/api/admin/integrity` повертає `healthy: true`.
5. Провести smoke-тест створення/редагування працівника, таймера, половини дня відпустки, погодження й відкликання.

Workflow-статуси, ролі, режими роботи, типи технічних записів і чотири погоджені категорії відшкодувань є доменними enum-ами, а не випадково захардкодженими кадровими даними. Їх змінюють лише окремою версійованою міграцією разом із бізнес-логікою.
